# R34 Browser

Local Next.js web UI for the rule34.xxx API. See `README.md` for setup and architecture, `RULE34_API.md` for the API documentation.

## Important

- **Next.js 16**: APIs and conventions may differ from training data. When in doubt, read the guides in `node_modules/next/dist/docs/` and heed deprecation notices.
- **API key stays server-side**: use `API_KEY`/`USER_ID` from `.env` only in `src/lib/r34.ts` and route handlers — never in client components or `NEXT_PUBLIC_` variables.
- **Rate limiting**: the API answers 429 when hit too hard (a burst of page fetches will do it, and it applies to the whole IP for a few minutes). `r34.ts` throws `UpstreamError` with the status, `/api/posts` passes 429 through as 429, and the grid says it is rate-limited instead of blaming the API for being down. A failed *later* page never discards the posts already on screen.
- **Missing credentials are their own state**: `r34.ts` throws `NotConfiguredError`, `/api/posts` maps it to 503 `{"error":"not configured"}` (an upstream 503 still becomes 502), and `PostGrid` renders setup instructions with a "Check again" button instead of the generic failure copy. `.env.example` is the committed template.
- **Upstream hardening** (`r34.ts`): both fetches carry `AbortSignal.timeout(10s)`, and responses are validated per item with `safeParse` — one malformed post drops that post, never the page. The posts route caps `tags` length (400) and clamps `page`.
- **A change that can't be saved is never silently swallowed**: the remaining localStorage writes go through `trySetItem` in `prefs.ts` (Safari private mode throws on every write), and a failed write to the shared store rolls its change back. Either one raises the same sticky warning banner in `AppHeader` (`useStorageWarning`).
- **API quirks** (handled in `src/lib/r34.ts`):
  - For zero results, the post API returns an empty body instead of `[]`.
  - The autocomplete endpoint requires a `Referer: https://rule34.xxx/` header.
  - Consecutive pages can contain the same post → deduplication by ID in `PostGrid`.
- Validate **Zod schemas** in `src/lib/types.ts` against real API responses before adding new fields.
- **Masonry is JS-based, not CSS columns** (`src/components/PostGrid.tsx`): posts are deterministically assigned to the shortest column (estimated via aspect ratio) so already visible posts don't move when infinite scroll appends pages. Don't switch back to CSS `columns-*` — that reintroduces the jumping. Column count comes from `matchMedia` breakpoints (sm 3 / lg 4 / xl 5); below `sm` a 1/2-column toggle persisted in localStorage applies (`useMobileColumns` in `src/app/page.tsx`).
- `PAGE_SIZE` (posts per request) lives in `src/lib/types.ts`.
- **State lives in SQLite on the server** (`src/lib/db.ts`, `src/lib/store.ts`, route `src/app/api/state/route.ts`): likes (capped at 2000), "not interested" dismissals (1000), the ids For You has already shown (2000), seed tags, blocked tags (25, no metatags — they would reshape a query rather than narrow it) and the tag metadata. The caps in `state.ts` are no longer about a browser quota — SQLite has room — they bound the *work of a page*: a like costs ~40 bytes as a ref on every page and ~1KB as a post in the Liked view. Raising one means asking which of the two grows. One dataset per instance, no auth, no user column — that is the point: every browser hitting the same server sees the same likes. Caps and the blocked-tag rules are enforced **in SQL, inside the same transaction as the write**, so a crash between insert and trim can't leave the store over its limit. `better-sqlite3` is native and listed in `serverExternalPackages`; the DB path comes from `DB_PATH` (default `data/r34-browser.sqlite`) and is read inside `getDb()`, never at module load.
- **Only three switches are still per-browser** (`src/lib/prefs.ts`): mobile column count, hide-AI and the rating filter. They keep the old localStorage machinery (`trySetItem`, the parsed-JSON cache, `useStoredJSON`). Everything else in that file is now a **mirror of the server state**: a module-level `content` object plus its own listener set, read through the same `useSyncExternalStore` hooks as before, so no consumer changed. `idSetOf` is unchanged and still load-bearing — the mirror hands back a referentially stable array, and every mounted card reads one shared Set instead of building its own. Cards are `content-visibility: auto`, which keeps a long feed out of the render path.
- **Writes are optimistic, written through, then reconciled**: `mutateSlice` in `prefs.ts` reads the *module-level* mirror (never the render closure, so two toggles in one tick can't clobber each other), paints the change, POSTs it, and adopts the slice the server answers with — that is how a cap eviction the client only guessed at gets corrected. A failed write rolls back and trips `useStorageWarning`. Each slice carries a ticket counter so a slow response can't drag the view back to a state the user has moved past. `recordSeen` is the exception: ids are only ever added, so it fires and forgets and never raises a warning.
- **Every page is hydrated with refs; tags are paid for where they are read** (`AppSnapshot` vs `TasteProfile` in `state.ts`): `layout.tsx` calls `readSnapshot(getDb())` directly (no HTTP call to itself) and passes it through `Providers`, which calls `hydrateContent` **during render, above `children`** — so the first frame already has the real state. That wave carries *refs only* — `{id, likedAt}` per like, `{id, dismissedAt}` per dismissal, plus seeds and blocked tags — which is all a card needs to fill its heart. Measured on a real store, dropping the tags took that payload from 63.8KB to 2.4KB. The heavy parts are fetched by the view that needs them: the full posts (`useLikedPosts`, Liked view), the tag metadata (`loadTagMeta`), and `useTaste` → `/api/state?part=taste` on the For You page. `layout.tsx` is `force-dynamic`: a prerendered shell would freeze build-time data into every page.
- **The taste profile is a window, not the whole history** (`readTaste`, `TASTE_WINDOW` = 500): the newest 500 likes and dismissals *with* their tags, oldest-first, plus the seen ids — the weights are recency-decayed anyway, so older entries barely move the result while their tags would still cross the wire. `useTaste` exposes `loading`, and For You renders "Reading your taste…" rather than flashing its cold-start hint at somebody with hundreds of likes. `TagMetaSync` reads the same window and is mounted by For You (not by `providers.tsx`, which would make every page fetch it).
- **The profile is kept in step locally, never refetched**: liking a post hands `rememberTasteLike` the tags of the post in hand, and `dropTasteEntriesGone` (called from `applySlice`) removes what the authoritative refs no longer contain — a cap eviction or an undismissal. `sessionLikes`/`sessionDismissals` exist for one race: a like made while the taste request was in flight is missing from the answer, so it is merged back in.
- `readSeen()`/`recordSeen()` stay synchronous non-hooks, and `readSeen()` returns a **copy** — a feed that snapshots the set once per run must not have it mutate underneath it. The set now arrives with the taste profile, so before that `readSeen()` is empty and `recordSeen` skips deduplication and lets the idempotent insert sort it out; For You re-snapshots it when `loading` flips.
- **Tag metadata** (`src/lib/tagmeta.ts`): `&fields=tag_info` on the post API returns each tag's site-wide count and category (tag/metadata/artist/character/copyright). It costs ~2.5KB per post, far too much for a 100-post feed page, so lookups are per post: `TagMetaSync` (mounted in `providers.tsx`) works through liked posts one at a time, and the lightbox calls `ensureTagMeta` for whatever the user opens — which colours its tag list by category *and* teaches the taste profile from posts that were only looked at. Results go into the `tag_meta` table (capped at 8000, LRU by a monotonic `touched` counter — a timestamp would collide inside one batch and evict the wrong row). The whole set is read into memory once per page load and mirrored there; `recordTagInfo` merges locally **first** and writes through fire-and-forget, because `TagMetaSync` reads its own writes to pick the next post. It is still a cache: a failed read or write costs uncoloured tags, never an error in front of the user. `fetchTagMetaForPost` throws on failed requests (transient — retryable) and resolves false only when a post genuinely has no tag info (permanent skip); `TagMetaSync` backs off for a minute after an error instead of hammering. Everything degrades gracefully when a tag is unknown.
- **For You recommendations** (`src/lib/recommend.ts`) are pure client-side heuristics: tag weights computed from liked posts (rare and identifying tags weigh more via `tagFactor`; `TAG_STOPLIST` is only the fallback for tags without metadata), single-tag and co-occurring tag-pair queries built by `buildForYouQueries`. Dismissals subtract from the profile via `applyDismissals` (at 0.7 of a like, so one bad post can't erase a shared artist or character), and posts shown in earlier runs are down-ranked rather than hidden — the seen set is snapshotted once per feed run, since a live one would re-rank posts under the reader. `scorePost` (raw weight sum) gates a post into the feed; `rankScore` (the same sum, damped by √tag-count) orders it. Ranking happens per fetched page inside `PostGrid`, never across the whole list — a global sort would move posts the user is already looking at. `PostGrid` decides each page's filtering and ranking **once, when the page arrives**, and caches it against that page's identity: liking a post rewrites the profile, and re-running those decisions would reshuffle what is already on screen. Actions that must take effect at once (dismissals) go through `excludeIds`, which is applied on every render. Shuffle uses the seeded `mulberry32` PRNG so a feed is reproducible until reshuffled.
- **Dialogs** (`ControlSheet`, `Lightbox`) share `useFocusTrap` (`src/lib/useFocusTrap.ts`): it counts only *rendered* controls, because the header and lightbox keep `sm:hidden` duplicates in the DOM and a display:none element can never take focus. Animated chrome carries `motion-reduce:transition-none`.
- **Content filters** (`contentFilterTags` in `prefs.ts`, UI in `ContentFilters.tsx`): rating, blocked tags and hide-AI compose into one query suffix used by both feeds — filtering happens upstream in the query, not by discarding results.
- **Pages**: `/` (search), `/for-you`, `/likes`; search tags sync to the URL.
- **Header/navigation** (`src/components/AppHeader.tsx`): all three pages share one header — don't re-add per-page header markup. Below `sm` navigation moves to `BottomNav` (fixed, rendered once in `layout.tsx`, so every `main` needs `pb-24 sm:pb-12`) and the secondary controls (sort, No AI, Shuffle, Taste) are passed as `controls` and rendered both inline (`sm:` and up) and inside `ControlSheet`; keep their state in `prefs.ts` or the owning page, never local to the passed nodes. The sheet renders as a sibling of `<header>` because the header's hide-on-scroll transform (`useHideOnScroll`) would otherwise become the containing block for its `fixed` positioning.
- **Lightbox** (`src/components/Lightbox.tsx`): pages the feed itself — the grid's scroll sentinel can't fire while the viewer holds the page still, so it calls `onNeedMore` (prefetching four posts before the end, once per page that arrives — the guard keys off `pagesLoaded`, not `posts.length`, because a page can arrive entirely filtered out) and lets its index run past the posts loaded so far, rendering a "loading" frame that becomes the post when the page lands. The `loaded` crossfade flag tracks the post's *identity*, since a dismissal or an arriving page can put a different post at the current index; "Not interested" stays at the index and lets the feed slide the next post in (stepping forward too would skip one). Opened from `MasonryColumns`, which owns the open index — it indexes into the `posts` array (load order), not into a column, so paging follows the feed rather than the layout. Cards stay `<a href={file_url}>` so modified clicks still open the raw file; the plain click is intercepted. Videos play inline (`autoPlay loop playsInline`); images show `sample_url` until `file_url` decodes, and the neighbours are prefetched. Keyboard: ←/→, `i`, Esc; touch: swipe left/right to page, swipe down to close.
- **Server logging** (`src/lib/log.ts`): `next start` logs no requests in production, so the container log shows only what the app writes. Routes log through `logInfo`/`logWarn`/`logError` as one `[scope] message` line; `logUpstreamFailure` turns 429, missing credentials, other upstream statuses and timeouts into a single line each, and only unexpected errors keep their stack. Search tags are never logged. A backup import logs kept/offered counts, and every refused import logs its reason.
- **Released images** (`.github/workflows/release.yml`): a `v*` tag publishes `ghcr.io/akana404/r34app` for `linux/amd64` and `linux/arm64`. Each architecture builds on its own native runner and pushes by digest; a merge job joins the two into one tagged manifest — emulating the ARM build would make `next build` and a possible `better-sqlite3` compile many times slower. `docker-compose.yaml` pulls that image; `docker-compose.build.yaml` is the overlay that builds from source instead. **No credential ever enters an image**: `.dockerignore` excludes `.env`/`.env.*`, and `API_KEY`/`USER_ID` are read from `process.env` at runtime, never inlined at build time. The runner stage takes its `node_modules` from a separate `npm ci --omit=dev` stage, so the toolchain doesn't ship — `next` itself is a real dependency, which is what keeps `npm start` working there.
- **No emoji in the UI** — icons are inline SVGs in `src/components/icons.tsx`.
- **Backup export/import** (`src/app/api/backup/route.ts`, buttons in `BackupControls` on the Liked page): `GET` downloads a JSON envelope (`{ app, version: 2, exportedAt, data }`) with likes *including* their posts (`readExport`), dismissals, seeds and blocked tags. Seen ids and tag metadata are caches: they are neither exported nor touched by an import (`replaceSnapshot` only replaces `seen`/`tagMeta` when given). `POST` always **replaces** (no merge), caps the body at 5 MB, and answers 422 for JSON that names none of the restorable fields, so a random file can't wipe the store. After a successful import the client does a full reload, because `hydrateContent` only takes the first snapshot of a page load. There is one parser, `normalizeBackup` in `src/lib/backup.ts`, shared with the CLI. `scripts/import-backup.mjs` (`npm run import-backup -- old/x.json`) cold-starts the database from an export of the old localStorage build (or from a new export, seen ids included); it reuses `replaceSnapshot` rather than growing a second write path, and `scripts/ts-resolve.mjs` is what lets plain node import the app's TS modules (it resolves the `@/` alias and adds file extensions).
