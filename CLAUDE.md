# R34 Browser

Local Next.js web UI for the rule34.xxx API. See `README.md` for setup and architecture, `RULE34_API.md` for the API documentation.

## Important

- **Next.js 16**: APIs and conventions may differ from training data. When in doubt, read the guides in `node_modules/next/dist/docs/` and heed deprecation notices.
- **API key stays server-side**: use `API_KEY`/`USER_ID` from `.env` only in `src/lib/r34.ts` and route handlers — never in client components or `NEXT_PUBLIC_` variables.
- **Rate limiting**: the API answers 429 when hit too hard (a burst of page fetches will do it, and it applies to the whole IP for a few minutes). `r34.ts` throws `UpstreamError` with the status, `/api/posts` passes 429 through as 429, and the grid says it is rate-limited instead of blaming the API for being down. A failed *later* page never discards the posts already on screen.
- **Missing credentials are their own state**: `r34.ts` throws `NotConfiguredError`, `/api/posts` maps it to 503 `{"error":"not configured"}` (an upstream 503 still becomes 502), and `PostGrid` renders setup instructions with a "Check again" button instead of the generic failure copy. `.env.example` is the committed template.
- **Upstream hardening** (`r34.ts`): both fetches carry `AbortSignal.timeout(10s)`, and responses are validated per item with `safeParse` — one malformed post drops that post, never the page. The posts route caps `tags` length (400) and clamps `page`.
- **localStorage writes never throw**: everything goes through `trySetItem` in `prefs.ts` (Safari private mode throws on every write; a heavy install can genuinely fill the quota). The first failure raises a sticky warning banner in `AppHeader` (`useStorageWarning`). `writePrefsSnapshot` is all-or-nothing with rollback so an import can't half-replace the store, and `recordTagInfo` evicts half its cache and retries before giving up.
- **API quirks** (handled in `src/lib/r34.ts`):
  - For zero results, the post API returns an empty body instead of `[]`.
  - The autocomplete endpoint requires a `Referer: https://rule34.xxx/` header.
  - Consecutive pages can contain the same post → deduplication by ID in `PostGrid`.
- Validate **Zod schemas** in `src/lib/types.ts` against real API responses before adding new fields.
- **Masonry is JS-based, not CSS columns** (`src/components/PostGrid.tsx`): posts are deterministically assigned to the shortest column (estimated via aspect ratio) so already visible posts don't move when infinite scroll appends pages. Don't switch back to CSS `columns-*` — that reintroduces the jumping. Column count comes from `matchMedia` breakpoints (sm 3 / lg 4 / xl 5); below `sm` a 1/2-column toggle persisted in localStorage applies (`useMobileColumns` in `src/app/page.tsx`).
- `PAGE_SIZE` (posts per request) lives in `src/lib/types.ts`.
- **All user preferences are client-side** (`src/lib/prefs.ts`): likes (capped at 500), "not interested" dismissals (300), the ids For You has already shown (2000), seed tags, blocked tags (25, no metatags — they would reshape a query rather than narrow it), the rating filter, hide-AI toggle, and mobile column count persist in localStorage via `useSyncExternalStore` hooks — there is no server-side storage. The parsed-JSON snapshot cache in there is load-bearing (referential stability), don't remove it — the shared id sets (`idSetOf`) hang off the same identity, so every mounted card reads one Set instead of building its own. Cards are `content-visibility: auto`, which keeps a long feed out of the render path.
- **Tag metadata** (`src/lib/tagmeta.ts`): `&fields=tag_info` on the post API returns each tag's site-wide count and category (tag/metadata/artist/character/copyright). It costs ~2.5KB per post, far too much for a 100-post feed page, so lookups are per post: `TagMetaSync` (mounted in `providers.tsx`) works through liked posts one at a time, and the lightbox calls `ensureTagMeta` for whatever the user opens — which colours its tag list by category *and* teaches the taste profile from posts that were only looked at. Results are cached in localStorage (`tagMeta`, capped at 8000 tags) as an **entry array, not a keyed object** — object keys that look like integers ("2023") always enumerate first, which broke the LRU eviction order; the legacy object shape is still readable. `fetchTagMetaForPost` throws on failed requests (transient — retryable) and resolves false only when a post genuinely has no tag info (permanent skip); `TagMetaSync` backs off for a minute after an error instead of hammering. Everything degrades gracefully when a tag is unknown.
- **For You recommendations** (`src/lib/recommend.ts`) are pure client-side heuristics: tag weights computed from liked posts (rare and identifying tags weigh more via `tagFactor`; `TAG_STOPLIST` is only the fallback for tags without metadata), single-tag and co-occurring tag-pair queries built by `buildForYouQueries`. Dismissals subtract from the profile via `applyDismissals` (at 0.7 of a like, so one bad post can't erase a shared artist or character), and posts shown in earlier runs are down-ranked rather than hidden — the seen set is snapshotted once per feed run, since a live one would re-rank posts under the reader. `scorePost` (raw weight sum) gates a post into the feed; `rankScore` (the same sum, damped by √tag-count) orders it. Ranking happens per fetched page inside `PostGrid`, never across the whole list — a global sort would move posts the user is already looking at. `PostGrid` decides each page's filtering and ranking **once, when the page arrives**, and caches it against that page's identity: liking a post rewrites the profile, and re-running those decisions would reshuffle what is already on screen. Actions that must take effect at once (dismissals) go through `excludeIds`, which is applied on every render. Shuffle uses the seeded `mulberry32` PRNG so a feed is reproducible until reshuffled.
- **Dialogs** (`ControlSheet`, `ImportDialog`, `Lightbox`) share `useFocusTrap` (`src/lib/useFocusTrap.ts`): it counts only *rendered* controls, because the header and lightbox keep `sm:hidden` duplicates in the DOM and a display:none element can never take focus. Animated chrome carries `motion-reduce:transition-none`.
- **Content filters** (`contentFilterTags` in `prefs.ts`, UI in `ContentFilters.tsx`): rating, blocked tags and hide-AI compose into one query suffix used by both feeds — filtering happens upstream in the query, not by discarding results.
- **Pages**: `/` (search), `/for-you`, `/likes`; search tags sync to the URL.
- **Header/navigation** (`src/components/AppHeader.tsx`): all three pages share one header — don't re-add per-page header markup. Below `sm` navigation moves to `BottomNav` (fixed, rendered once in `layout.tsx`, so every `main` needs `pb-24 sm:pb-12`) and the secondary controls (sort, No AI, Shuffle, Taste) are passed as `controls` and rendered both inline (`sm:` and up) and inside `ControlSheet`; keep their state in `prefs.ts` or the owning page, never local to the passed nodes. The sheet renders as a sibling of `<header>` because the header's hide-on-scroll transform (`useHideOnScroll`) would otherwise become the containing block for its `fixed` positioning.
- **Lightbox** (`src/components/Lightbox.tsx`): pages the feed itself — the grid's scroll sentinel can't fire while the viewer holds the page still, so it calls `onNeedMore` (prefetching four posts before the end, once per page that arrives — the guard keys off `pagesLoaded`, not `posts.length`, because a page can arrive entirely filtered out) and lets its index run past the posts loaded so far, rendering a "loading" frame that becomes the post when the page lands. The `loaded` crossfade flag tracks the post's *identity*, since a dismissal or an arriving page can put a different post at the current index; "Not interested" stays at the index and lets the feed slide the next post in (stepping forward too would skip one). Opened from `MasonryColumns`, which owns the open index — it indexes into the `posts` array (load order), not into a column, so paging follows the feed rather than the layout. Cards stay `<a href={file_url}>` so modified clicks still open the raw file; the plain click is intercepted. Videos play inline (`autoPlay loop playsInline`); images show `sample_url` until `file_url` decodes, and the neighbours are prefetched. Keyboard: ←/→, `i`, Esc; touch: swipe left/right to page, swipe down to close.
- **No emoji in the UI** — icons are inline SVGs in `src/components/icons.tsx`.
- **Backup/restore** (`src/lib/backup.ts`, UI in the Liked page header): exports the whole localStorage state as versioned JSON (`{ app, version, exportedAt, data }`) and imports it after a confirmation dialog offering merge (union of likes by id, newest `likedAt` wins, entries carrying the full post preferred) or replace. Reads/writes go through `readPrefsSnapshot`/`writePrefsSnapshot` in `prefs.ts` so the storage keys stay in one place; bump `VERSION` when the payload shape changes.

## Testing

- `npm test` (vitest) covers the pure logic (`recommend`, `backup`, `r34`, `types`), the localStorage stores (`prefs`, `tagmeta`, jsdom), the API route handlers, and the components that carry real logic (`PostGrid`, `MasonryColumns`, `Lightbox`, `SearchBar`, `AppHeader`).
- Component and store tests opt into jsdom per file with `// @vitest-environment jsdom`, and register `afterEach(cleanup)` themselves — vitest globals are off.
- Gotchas: jsdom has no `matchMedia` or `IntersectionObserver`, so grid tests stub both; the DOM order of a masonry grid is column-major, so tests that assert feed order render with `mobileColumns={1}`.
- End-to-end checks (real API, real browser) still live in `.claude/skills/verify`.
